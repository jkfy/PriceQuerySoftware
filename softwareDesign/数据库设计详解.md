## 1. 四个脚本是什么关系

| 脚本 | 性质 | 内容 | 为什么单独拆出来 |
|---|---|---|---|
| `01_schema.sql` | DDL | 建库、12 张表、2 个视图、索引、外键 | 结构变更要能单独重放 |
| `02_logic.sql` | 存储程序 | 2 个触发器 + 2 个存储过程 | 含 `DELIMITER`，与纯 DDL 混合容易出错；且逻辑变更频率高于结构 |
| `03_sample_data.sql` | DML | 1 产品 → 2 部件 → 5 元件 | 开发/演示数据，生产环境不执行 |
| `04_verify.sql` | 只读查询 | 展开、汇总、缺价、检索、追溯 | 每次改完脚本跑一遍，30 秒确认没坏 |

**顺序不能乱**：`02` 的触发器引用了 `item`/`bom_edge`，必须在 `01` 之后；`03` 插入数据时会被 `02` 的触发器校验，所以 `02` 必须在 `03` 之前。如果 `03` 先跑，插进去的脏结构（比如产品当子件）当时不报错，等 `02` 建好触发器后也不会回溯检查——数据就悄悄坏了。

> 这也说明一个通用原则：**能被数据库约束表达的规则，越早建立越好**，否则历史数据永远是漏网的。

## 2. 先看业务：数据是怎么流动的

整套表围绕三个动作，搞清这三条数据流，表结构就不用背了。

### 2.1 历史价格录入（Excel → 库）

```
Excel 文件
   │  ① 整批登记
   ▼
import_batch（批次：文件名、SHA256、模板版本、统计）
   │  ② 每行原样落库
   ▼
import_row（行号、raw_json 原始单元格、解析出的编号/数量/金额）
   │  ③ 按 item_code / item_alias 匹配
   ▼
item（匹配成功的物料）
   │  ④ 元件的价格写入；部件/产品的价格只用于校验
   ▼
price_record(price_kind='direct')     ← 参与计算
price_record(price_kind='reported')   ← 只做对账
```

关键点：**`import_row` 是证据，`price_record` 是结论**。原始行永远留着，事后能回答“这条 800 块是哪天、哪个文件、第几行导进来的”。

### 2.2 Excel 报价查询（Excel → 展开 → 快照）

```
import_batch(type='quote_request')
   │
   ▼
逐行匹配 item
   │
   ├─ 匹配到，且是产品/部件 → 从 bom_edge 递归展开
   ├─ 匹配到，是元件       → 直接用单价
   └─ 没匹配到 / 没价格    → price_state='missing'，金额按 0，标灰
   │
   ▼
后序遍历汇总（叶子：数量×单价；父节点：子节点求和）
   │
   ▼
quotation + quotation_line（快照，价格从此冻结）
```

### 2.3 在线选型（下拉逐级选）

和 2.2 后半段完全一样，只是行的来源不是 Excel，而是用户在界面上的选择，所以 `quotation.source='selector'`、`quotation_line.line_source='input'`。

**这就是为什么三种查询能共用一套表**：差异只在“输入从哪来”，展开、计价、展示、导出完全一致。

## 3. `01_schema.sql`：结构与语法

### 3.1 文件头：字符集的三个层次

```sql
CREATE DATABASE IF NOT EXISTS `price_query`
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_ai_ci;

SET NAMES utf8mb4;
```

MySQL 的字符集有三个独立层次，缺一层就会乱码：

| 层次 | 在哪设 | 作用 |
|---|---|---|
| 服务器/库/表/列 | `CREATE DATABASE ... CHARSET` | 数据**存**成什么编码 |
| 连接（客户端↔服务器） | `SET NAMES utf8mb4` | 传输时**编解码** |
| 排序规则（collation） | `COLLATE` | 比较和排序**怎么算相等** |

`SET NAMES utf8mb4` 等价于一次设三个变量：

```sql
SET character_set_client     = utf8mb4;  -- 客户端发来的字节按什么解释
SET character_set_connection = utf8mb4;  -- 连接层转换目标
SET character_set_results    = utf8mb4;  -- 结果按什么编码返回
```

**为什么必须 utf8mb4 而不是 utf8**：MySQL 的 `utf8` 是 `utf8mb3` 的别名，最多 3 字节，存不了 emoji 和部分生僻字（如「𠮷」「㈱」）。Excel 导入的备注里出现一个 emoji，`utf8mb3` 就会报 `Incorrect string value`，或者更糟——非严格模式下悄悄截断。

**`utf8mb4_0900_ai_ci` 这个名字拆开看**：

| 片段 | 含义 |
|---|---|
| `utf8mb4` | 字符集（4 字节 UTF-8） |
| `0900` | 基于 Unicode 9.0 的 UCA 排序算法 |
| `ai` | accent-insensitive，重音不敏感：`café` = `cafe` |
| `ci` | case-insensitive，大小写不敏感：`ABC` = `abc` |

大小写不敏感对料号匹配是**刚需**——客户 Excel 里写 `c-3001`，库里存 `C-3001`，必须能匹配上。实测：

```sql
SELECT item_code FROM item WHERE item_code = 'c-3001';
-- 返回 C-3001（命中）
```

代价是：`uk_item_code` 下 `ABC-01` 和 `abc-01` 会被判定为重复，插入报 `ERROR 1062`。这是刻意的——同号不同大小写只会制造混乱。

> 如果某些字段需要**区分大小写**（比如密码哈希、Base64），单独给它指定 `COLLATE utf8mb4_0900_as_cs`（`as` = accent-sensitive，`cs` = case-sensitive）。

### 3.2 `SET FOREIGN_KEY_CHECKS = 0`

```sql
SET FOREIGN_KEY_CHECKS = 0;   -- 开头
...
SET FOREIGN_KEY_CHECKS = 1;   -- 结尾
```

这是**会话级**开关，只影响当前连接。用它有两个场景：

1. **DROP 顺序**：删表时如果子表还引用父表，会报 `ERROR 1217`。关掉检查就不用careful地排顺序（但我还是按反依赖顺序写了，方便阅读）。
2. **大批量导入**：几万行数据逐行检查外键很慢，可以关掉再开，但必须自己保证数据一致——**这是个危险操作**，只在确定数据干净时用。

`SET NAMES` / `SET FOREIGN_KEY_CHECKS` 都不是标准 SQL，是 MySQL 方言；换库时要改。

### 3.3 `item`：一张表装三种物料

```sql
CREATE TABLE `item` (
  `id`          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `item_code`   VARCHAR(64)  NOT NULL,
  `item_name`   VARCHAR(255) NOT NULL,
  `item_type`   ENUM('component','assembly','product') NOT NULL,
  ...
  UNIQUE KEY `uk_item_code` (`item_code`),
  KEY `idx_item_type_status` (`item_type`, `status`),
  FULLTEXT KEY `ft_item_name_spec` (`item_name`, `spec`) WITH PARSER ngram
)
```

**业务映射**：三种物料共用一张表，因为字段完全一致，差异只在“能不能有子件”“价格从哪来”，属于**行为差异**而不是**结构差异**。

#### 主键类型：为什么是 `BIGINT UNSIGNED`

| 类型 | 字节 | 上限 | 适用 |
|---|---|---|---|
| `INT` | 4 | 21 亿 | 一般够 |
| `BIGINT` | 8 | 922 亿亿 | 物料表其实用不到 |
| `BIGINT UNSIGNED` | 8 | 1844 亿亿 | 统一风格，成本一样 |

选 `BIGINT UNSIGNED` 不是为了“真会有那么多”，而是**统一所有表的关联列类型**。外键两端的类型必须完全一致（包括符号），否则建外键直接报错。全库统一成一种，省得每加一张表就要想一遍。

#### `ENUM` 的取舍

`ENUM` 底层存的是**整数序号**（值少于 256 个时占 1 字节），不是字符串：

| 值 | 存储 |
|---|---|
| `component` | 1 |
| `assembly` | 2 |
| `product` | 3 |

好处：省空间、强校验（写入非法值直接报错）。
代价：**排序按定义顺序，不是字母序**。实测：

```sql
SELECT item_type FROM item GROUP BY item_type ORDER BY item_type;
-- component
-- assembly
-- product        ← 按定义顺序，不是 a/p/p 的字母序
```

这个特性有时正好有用（元件→部件→产品的展示顺序），但如果你是想要字母序，就会得到意外结果。另一种坑：`ALTER TABLE ... MODIFY COLUMN item_type ENUM(...)` 加值时，**追加到末尾**是 INSTANT 操作，**插到中间**要重建整表——所以永远把新枚举值加在最后。

> 替代方案：`TINYINT` + 一张 `dict_item_type` 字典表。优点是新增类型不用改表结构，缺点是查询要 JOIN。本系统类型固定为三种，`ENUM` 更划算。

#### 唯一键与命名空间

`uk_item_code` 建在 `item_code` 上，**三类物料共用一个命名空间**。这意味着不能同时存在元件 `C-3001` 和部件 `C-3001`。

为什么这样设计：报价查询时用户只给一个编号，系统必须能唯一确定是哪个物料。如果允许同号异构，匹配逻辑就要加二次判断，而且客户 Excel 里也不会区分。

**软删除与唯一键的冲突**：`status=-1` 的物料仍占着编号，想用同一个编号新建就会撞 `1062`。如果业务上需要“删了能复用编号”，用**函数索引**：

```sql
-- 只有未删除的行参与唯一性检查（MySQL 8.0.13+）
ALTER TABLE item DROP INDEX uk_item_code,
  ADD UNIQUE KEY uk_item_code_alive ((IF(status <> -1, item_code, NULL)));
```

原理：`status=-1` 时表达式求值为 `NULL`，而**唯一索引允许多个 NULL**（NULL 不等于 NULL），所以已删除的行不冲突。

#### 索引：最左前缀

```sql
KEY `idx_item_type_status` (`item_type`, `status`)
```

这个索引能服务：

- `WHERE item_type = 'component'` ✅
- `WHERE item_type = 'component' AND status = 1` ✅
- `WHERE status = 1` ❌（跳过了最左列，用不上）

**最左前缀原则**：复合索引像电话簿先按姓、再按名排序，你只知名而不知姓，就没法用这个排序。所以设计复合索引时，把**区分度低但必填**的列放左边，把**筛选性强的**放右边——或者干脆按查询模式的顺序来。

#### 全文索引与中文分词

```sql
FULLTEXT KEY `ft_item_name_spec` (`item_name`, `spec`) WITH PARSER ngram
```

MySQL 默认的全文分词器按**空格和标点**切词。中文没有空格，`"接线端子"` 会被当成一个完整的词，你搜「端子」就搜不到——这就是很多人说“MySQL 全文索引对中文没用”的原因。

`ngram` 分词器（MySQL 5.7.6+ 内置）把文本切成**固定长度的字串**，`ngram_token_size` 默认 2，即二元切分：

```
接线端子  →  接线 / 线端 / 端子
```

所以搜「端子」能命中。实测：

```sql
SELECT item_code, item_name FROM item
WHERE MATCH(item_name, spec) AGAINST ('端子' IN BOOLEAN MODE);
-- C-3001  接线端子
```

三个注意点：

1. 查询词**短于 `ngram_token_size`**（即单字）匹配不到，搜「端」会空。
2. `MATCH` 必须直接用**建了全文索引的列**，且不能加 `OR` 去混别的条件（优化器会退化成全表扫描）。
3. 全文索引只服务 `MATCH ... AGAINST`，`LIKE '%端子%'` 用不上它。

#### 时间戳列

```sql
`created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
`updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

`ON UPDATE CURRENT_TIMESTAMP` 有个**反直觉的行为**：如果 UPDATE 前后值完全相同，时间戳**不会更新**。想强制更新必须显式写 `updated_at = NOW()`。

另外 `DATETIME` 与 `TIMESTAMP` 的区别要清楚：

| | `DATETIME` | `TIMESTAMP` |
|---|---|---|
| 存储 | 原样存字面值 | 存 UTC，取出按会话时区转换 |
| 范围 | 1000–9999 年 | 1970–2038 年 |
| 时区 | 不敏感 | 敏感 |

本系统是单机 Windows 使用，`DATETIME` 更省心（不会因为换台机器时区不同就“穿越”）。

### 3.4 `item_category`：一个自引用表的经典陷阱

```sql
CREATE TABLE `item_category` (
  `id`        INT UNSIGNED NOT NULL AUTO_INCREMENT,
  `name`      VARCHAR(64)  NOT NULL,
  `parent_id` INT UNSIGNED NULL,       -- NULL 表示根分类
  ...
  UNIQUE KEY `uk_cat_name_parent` (`parent_id`, `name`)
);
```

**坑在这里**：`UNIQUE(parent_id, name)` 想表达“同一父分类下名称不重复”，但 SQL 里 **`NULL` 不等于 `NULL`**，所以所有 `parent_id IS NULL` 的根分类**不受唯一性约束**——可以建两个都叫「电气件」的根分类。

这是 SQL 三值逻辑的必然结果（`NULL = NULL` 结果是 `UNKNOWN` 而不是 `TRUE`）。三种解法：

1. 根节点的 `parent_id` 用 `0` 而不是 `NULL`（用 0 表示“无父级”）；
2. 加生成列，把 NULL 转成 0，再对生成列建唯一索引；
3. 应用层校验（最弱）。

分类树在本系统里是辅助功能，我保留了 `NULL` 语义（更符合直觉），如果真出现重名根分类，是应用的校验责任。

### 3.5 `item_alias`：为什么 `source` 必须 NOT NULL

```sql
`source` VARCHAR(64) NOT NULL DEFAULT '' COMMENT '来源标识：客户A / 旧ERP / 供应商X',
UNIQUE KEY `uk_alias` (`source`, `alias_code`)
```

如果 `source` 允许 `NULL`，唯一键就形同虚设——`(NULL, 'KH-001')` 可以插入无数次，因为 NULL 互不相等。**唯一索引里的可空列是个定时炸弹**，所以这里用 `NOT NULL DEFAULT ''`。

业务上这张表解决的是：“客户 A 给的 Excel 里写的是 `KH-DZ-001`，我们库里叫 `C-3001`”。没有这一层，导入匹配率会低得离谱。

`ON DELETE CASCADE`：物料删了，它的别名没有任何保留价值，跟着删。

### 3.6 `bom_edge`：全库最核心的三列

```sql
CREATE TABLE `bom_edge` (
  `parent_id`  BIGINT UNSIGNED NOT NULL,
  `child_id`   BIGINT UNSIGNED NOT NULL,
  `quantity`   DECIMAL(18,4) NOT NULL DEFAULT 1.0000,
  `seq_no`     INT NOT NULL DEFAULT 0,
  PRIMARY KEY (`parent_id`, `child_id`),
  KEY `idx_edge_parent_seq` (`parent_id`, `seq_no`),
  KEY `idx_edge_child` (`child_id`),
  CONSTRAINT `ck_edge_qty` CHECK (`quantity` > 0)
)
```

#### 为什么用复合主键而不是自增 id

InnoDB 是**聚簇索引**（clustered index）表：数据行物理上按主键顺序存放。主键是 `(parent_id, child_id)`，意味着同一个父件的所有子件**在磁盘上连续排列**。

展开一个产品的 BOM，就是反复执行 `WHERE parent_id = ?`——命中聚簇索引，**顺序读**。如果改成自增 `id` 主键，同样的查询要查二级索引 `(parent_id)` 拿到一堆 `id`，再逐个**回表**（随机读），磁盘 IO 差一个数量级。

额外好处：

- 天然去重（同一子件在同父件下只能出现一次）；
- 省一个自增列和一份索引空间；
- 二级索引 `idx_edge_child(child_id)` 内部实际存储的是 `(child_id, parent_id)`——因为 InnoDB 的二级索引**自动带上主键列**。所以“反查某元件被谁用”不需要回表。

#### 用量为什么在边上

同一个「接线端子」，装在线束里用 10 个，装在别处可能用 2 个。**用量是关系的属性，不是物料的属性**。这是这类系统最常见的建模错误：把 `quantity` 放进 `item` 表，结果改一个产品的用量，所有产品的用量全变了。

#### `DECIMAL(18,4)` 而不是 `FLOAT/DOUBLE`

`DECIMAL(18,4)` = 总共 18 位有效数字，其中 4 位小数；整数部分最多 14 位（最大 `99999999999999.9999`），足够表示任何报价金额。

**金额绝不能用浮点数**：`0.1 + 0.2` 在二进制浮点里等于 `0.30000000000000004`，累加几百行后差额会累积成“报价少了 3 分钱”这种无法解释的问题。`DECIMAL` 是定点数，精确。

#### `CHECK` 约束

```sql
CONSTRAINT `ck_edge_qty` CHECK (`quantity` > 0)
```

**MySQL 8.0.16 之前，`CHECK` 只是被解析后忽略**（语法通过，但不生效），所以很多老资料说“MySQL 不支持 CHECK”。8.0.16 起才真正强制。实测违反时：

```sql
ERROR 3819 (HY000): Check constraint 'ck_edge_qty' is violated.
```

`CHECK` 的限制：不能有子查询、不能引用其它表、不能用非确定性函数（`NOW()`、`RAND()`）。**跨表规则它做不到**，那正是触发器的活（见 4.2）。

#### 外键动作的不对称设计

```sql
CONSTRAINT `fk_edge_parent` FOREIGN KEY (`parent_id`) REFERENCES `item`(`id`) ON DELETE CASCADE,
CONSTRAINT `fk_edge_child`  FOREIGN KEY (`child_id`)  REFERENCES `item`(`id`) ON DELETE RESTRICT
```

| 动作 | 含义 | 用在哪 |
|---|---|---|
| `CASCADE` | 父记录删除时，子记录跟着删 | 父件没了，它的 BOM 明细自然没意义 |
| `RESTRICT` / `NO ACTION` | 有引用时禁止删除 | 元件被别处用着，不许删，否则别人的产品 BOM 断链 |
| `SET NULL` | 父记录删除时，外键置空（列必须可空） | 报价单里引用的物料被删，保留快照但断开关联（见 `quotation_line.item_id`） |

这个不对称是**业务规则的物理表达**：删产品可以连锅端，删元件必须先解绑。即便有人绕过界面直接跑 SQL，这条规则依然生效。

#### 外键的隐式索引

InnoDB 要求外键列必须有索引，**如果没有，它会自动建一个**——名字是自动生成的（如 `fk_edge_child` 对应的索引可能叫 `child_id`），以后想改名很麻烦。所以我在建表时显式声明了 `idx_edge_child`，把命名权握在手里。

### 3.7 `price_record`：一个字段。

```sql
CREATE TABLE `price_record` (
  `item_id`       BIGINT UNSIGNED NOT NULL,
  `price_kind`    ENUM('direct','reported') NOT NULL DEFAULT 'direct',
  `amount`        DECIMAL(18,4) NOT NULL,
  `price_date`    DATE NOT NULL,
  ...
  UNIQUE KEY `uk_price_item_kind_date` (`item_id`, `price_kind`, `price_date`),
  CONSTRAINT `ck_price_amount` CHECK (`amount` >= 0)
)
```

#### `price_kind` 是整个设计的支点

| 值 | 载体 | 含义 | 参与计算 |
|---|---|---|---|
| `direct` | 元件 | 人工录入 / Excel 导入的**单价** | ✅ 唯一输入 |
| `reported` | 部件/产品 | Excel 里给出的**成交总价** | ❌ 只做对账 |

一个 `amount` 字段承载两种语义，靠 `price_kind` 区分。这是**有意的权衡**：

- 优点：一张表、一套索引、一套历史查询逻辑，`v_item_direct_price` 一个视图就搞定。
- 缺点：字段含义依类型而变，读代码的人必须先看 `price_kind`。

替代方案是拆成两个字段（`unit_price` / `total_price`），可读性更好，但会出现“两个字段一空一满”的行，且每个查询都要写 `COALESCE`。在只有两种价格、且语义互斥的前提下，单字段更紧凑。

#### 唯一三元组 = 幂等导入

`UNIQUE(item_id, price_kind, price_date)` 带来一个非常有用的性质：**同一天、同一物料、同一类价格只可能有一条**。于是导入可以用 `ON DUPLICATE KEY UPDATE` 实现“**重导即修正**”：

```sql
INSERT INTO price_record (item_id, price_kind, amount, price_date, source)
VALUES (4, 'direct', 3.0000, '2026-01-01', 'manual')
ON DUPLICATE KEY UPDATE amount = VALUES(amount);
```

实测：第二次执行影响行数为 **2**（表示“更新了”，插入是 1，值没变是 0）。所以用户发现昨天导错了，今天重导一次就覆盖，不会产生重复价格。

> 如果业务上存在“同一元件一天内多次成交、价格不同”，就要去掉这个唯一键，改成普通索引，查询时用 `ORDER BY price_date DESC, id DESC LIMIT 1` 取最新。改动只影响一个视图。

#### 日期版本化的威力

价格带 `price_date`，查询时取“基准日之前最新的一条”。于是：

- 今天导入 2023 年的历史成交价，**不会污染当前报价**（当前价取自 2024/2025 的记录）；
- 可以回答“按 2025-06-30 的价格重算这张报价单”；
- 历史可追溯，不需要额外的“价格变更日志表”。

#### 索引与反向扫描

唯一键 `(item_id, price_kind, price_date)` 已经能服务“取某物料最新价”：

```sql
SELECT ... FROM price_record
WHERE item_id = 4 AND price_kind = 'direct'
ORDER BY price_date DESC LIMIT 1;
```

InnoDB 支持**反向扫描索引**，所以 `DESC` 不需要单独建降序索引。（早期版本加的那条 `idx_price_item_date(... DESC)` 是冗余的，已经删掉——多一条索引就多一份写入成本和缓冲池占用。）

#### 后置外键：建表顺序问题

`price_record.import_row_id` 指向 `import_row`，但 `import_row` 又指向 `item`，而 `price_record` 在 `import_row` 之前创建。所以外键在建表后补：

```sql
ALTER TABLE `price_record`
  ADD CONSTRAINT `fk_price_import_row`
  FOREIGN KEY (`import_row_id`) REFERENCES `import_row` (`id`) ON DELETE SET NULL;
```

这不是循环依赖，只是**文件里的书写顺序**。如果非要在一张 `CREATE TABLE` 里写完，就得调整章节顺序，反而更难读。用 `ALTER TABLE` 补是标准做法。

### 3.8 两个视图

```sql
CREATE OR REPLACE VIEW `v_item_direct_price` AS
SELECT r.`item_id`, r.`amount`, r.`currency`, r.`price_date`, r.`source`
FROM `price_record` r
WHERE r.`price_kind` = 'direct'
  AND r.`price_date` = (
        SELECT MAX(r2.`price_date`)
        FROM `price_record` r2
        WHERE r2.`item_id` = r.`item_id`
          AND r2.`price_kind` = 'direct'
      );
```

**视图的本质**：一条被存起来的 `SELECT`，**不存数据、不能建索引**。每次查询视图，MySQL 把它展开成对基表的查询（`ALGORITHM=MERGE`，即“合并”）。含聚合、`DISTINCT`、`UNION` 时会退化成 `ALGORITHM=TEMPTABLE`——先物化成临时表再查，性能差一截。

#### 为什么用相关子查询而不是 `GROUP BY + JOIN`

```sql
-- 也可以这么写
SELECT r.* FROM price_record r
JOIN (SELECT item_id, MAX(price_date) md FROM price_record
      WHERE price_kind='direct' GROUP BY item_id) t
  ON t.item_id = r.item_id AND t.md = r.price_date;
```

两种写法结果一样。选相关子查询的理由：

1. 视图定义里**子查询放在 `FROM` 子句**有版本限制，而**相关子查询放在 `WHERE`** 一直没问题；
2. 遇到 `price_date` 相同但 `id` 不同的脏数据时，相关子查询可能返回两行，`JOIN` 版本也一样——行为可预期；
3. 可读性上，“这一行的日期等于它自己的最大日期”更接近业务语言。

性能上两者都能用上 `uk_price_item_kind_date`：子查询是索引上的 `MAX()`，属于索引跳跃/松散扫描，不是逐行全表。

#### 第二个视图：为什么用 LEFT JOIN

```sql
CREATE OR REPLACE VIEW `v_item_search` AS
SELECT i.`id` AS `item_id`, ..., p.`amount` AS `direct_price`, p.`price_date`
FROM `item` i
LEFT JOIN `v_item_direct_price` p ON p.`item_id` = i.`id`
WHERE i.`status` <> -1;
```

用 `LEFT JOIN` 而不是 `INNER JOIN`，**没有价格的物料必须保留**——否则“缺价清单”永远是空的，而这正是需求里要重点提示的东西。没价格时 `direct_price` 为 `NULL`，应用层据此标灰。

`WHERE i.status <> -1` 只过滤“已删除”，**停用（0）的物料仍然可见**——停用是“不再采购”，不是“从系统消失”，历史报价还要能查。

注意 `v_item_search.item_id` 这个别名是刻意写的：库里其它表都用 `item_id`，视图如果暴露成 `id`，关联时容易写错。实测输出：

```
item_id | item_code | item_type | direct_price
      4 | C-3001    | component | 2.5000
      8 | C-3005    | component | NULL      ← 无价，保留
```

#### 视图里不能干的事

- 不能用 `MATCH ... AGAINST` 走全文索引（全文索引建在基表上）——所以 4.4 节的检索直接查 `item`；
- 不能有 `FROM` 子句里的子查询（各版本限制不同，别赌）；
- 不能引用用户变量、临时表；
- 窗口函数、CTE 在视图定义里各小版本支持不一，别依赖。

### 3.9 `import_batch` / `import_row`

```sql
CREATE TABLE `import_row` (
  `id`              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `batch_id`        BIGINT UNSIGNED NOT NULL,
  `row_no`          INT NOT NULL,
  `raw_json`        JSON NOT NULL,
  `computed_amount` DECIMAL(18,4) NULL,
  `match_type`      ENUM('exact','alias','fuzzy','none') NULL,
  `row_status`      ENUM('ok','warn','error') NOT NULL DEFAULT 'ok',
  ...
  UNIQUE KEY `uk_row_batch_no` (`batch_id`, `row_no`)
)
```

#### `JSON` 类型值不值得用

`raw_json` 存整行原始单元格。用 `JSON` 而不是 `TEXT` 的好处：

- **写入时校验合法性**，存不进坏 JSON；
- 内部是二进制格式，读取比 `TEXT` 快；
- 支持路径查询：`raw_json->>'$.单价'`、`JSON_EXTRACT(raw_json, '$.编号')`。

代价：**不能直接建普通索引**。如果哪天要按 JSON 里的某个字段查，需要加**生成列**再建索引：

```sql
ALTER TABLE import_row
  ADD COLUMN supplier VARCHAR(64)
    GENERATED ALWAYS AS (raw_json->>'$.供应商') STORED,
  ADD KEY idx_supplier (supplier);
```

这个设计的意义：需求里两张 Excel 模板都还“待定”。模板一变，`import_row` 表结构不用动——原始数据全在 JSON 里，解析逻辑改代码即可。

#### 为什么 `computed_amount` 和 `amount` 并存

- `amount`：Excel 里写的价格（历史成交价）；
- `computed_amount`：系统按 BOM 明细算出来的价格。

两列并排放，**差额一眼可见**，而且能直接 `SELECT ... WHERE amount <> computed_amount` 导出“对不上账”的清单。如果只存一个，就得重新算一遍才能对比。

#### `CHAR(64)` 存 SHA256

`file_sha256 CHAR(64)`：SHA256 的十六进制表示固定 64 个字符，用 `CHAR` 而不是 `VARCHAR`——定长，不用存长度前缀。用途是**防重复导入**：同一个文件导两次，先查 `WHERE file_sha256 = ?` 就能拦住。

#### 批次表的意义

`import_batch` 是**事务边界 + 可追溯单元**：

- `status` 状态机 `running → success/partial/failed`，程序崩溃后能看出哪批没跑完；
- `total_rows / ok_rows / fail_rows` 让用户一眼看到“120 行，3 行失败”；
- 级联删除：删批次连带删明细（`ON DELETE CASCADE`），但**不动已经写入的价格**——价格是独立事实。

### 3.10 `quotation` / `quotation_line`：快照

```sql
CREATE TABLE `quotation_line` (
  `quotation_id`   BIGINT UNSIGNED NOT NULL,
  `parent_line_id` BIGINT UNSIGNED NULL,   -- 故意不加外键
  `item_id`        BIGINT UNSIGNED NULL,   -- 允许空：库里没这个物料
  `item_code`      VARCHAR(64) NOT NULL,   -- 快照
  `item_name`      VARCHAR(255) NOT NULL,
  `sort_key`       VARCHAR(255) NOT NULL DEFAULT '',
  `price_state`    ENUM('priced','missing','zero','manual') NOT NULL DEFAULT 'priced',
  ...
)
```

#### 为什么存快照而不是实时算

报价单是**对外承诺**。三个月后元件涨价，客户拿着当时的报价单来对账，你必须能原样复现。所以 `quotation_line` 把单价、金额、编号、名称全部冻结——**不 JOIN `item` 也能还原整张单**。

这也解释了 `item_id` 为什么允许 `NULL`：Excel 里出现了库里没有的物料，这一行仍然要展示、要标灰、要能导出成“待询价清单”。如果强制外键非空，这类行就进不了库，需求直接做不了。

#### 树的三种存法

| 方案 | 结构 | 查子树 | 移动节点 | 适合 |
|---|---|---|---|---|
| **邻接表**（`bom_edge`） | 存 `parent_id` | 递归 CTE | 改一行 | 写多读少、层级浅 |
| **物化路径**（`sort_key`） | 存 `001.002.003` | `LIKE '001.002%'` | 重写子树 | 读多写少、排序固定 |
| **嵌套集**（`lft/rgt`） | 存左右值 | `BETWEEN` | 重算大片 | 几乎不改结构 |

有意思的是：**BOM 用邻接表，报价单用物化路径**。原因是二者读写特性相反：

- BOM 会被频繁修改（改产品结构），深度只有 3~4 层，递归成本低 → 邻接表；
- 报价单一旦生成就冻结，只读、要按顺序展示、要一键导出 → `sort_key` 字符串排序一次 `ORDER BY` 就还原整棵树，零递归。

`sort_key` 用 `LPAD(seq_no, 3, '0')` 补零，是为了让字符串排序等价于数字排序（不然 `10` 会排在 `2` 前面）。实测输出里 `001.010.020` 这种结构就是它生成的。

#### `price_state` 四态

| 值 | 含义 | 界面 |
|---|---|---|
| `priced` | 有价格 | 正常黑色 |
| `missing` | 库里没有这个物料，或没有价格 | 灰色，金额 0 |
| `zero` | 价格确实是 0（赠品/自制件） | 正常，但要有标记 |
| `manual` | 用户手工改过价 | 黄色底 |

只有把 `missing` 和 `zero` 分开，才能回答“这张报价单里哪些是真的免费、哪些是漏录了价格”。

#### 为什么 `parent_line_id` 不加外键

自引用外键 + `ON DELETE CASCADE` 在 MySQL 里是允许的，但删除一棵树时会**逐层级联**，而 MySQL 对级联深度有限制（15 层）。更重要的是：删 `quotation` 时，级联删 `quotation_line` 和自引用级联可能同时触发，行为不够直观。

这里 `parent_line_id` 只是**展示用的层级关系**，完整性由应用维护（父行一定先插入）。加索引保证查询性能，不加外键换取可预测性。

#### `total_amount` vs `priced_amount`

缺价行金额按 0 计入 `total_amount`，这会让合计“看起来正常”实则偏低。所以单独存一个 `priced_amount`（只累加有效价格），再存 `missing_count`。导出时界面可以显示“合计 ¥981.00（其中 1 项缺价，未计入）”。

```sql
CREATE TABLE `audit_log` (

  `entity_id`   BIGINT UNSIGNED NULL,
  `action`      ENUM('create','update','delete','import','export','login') NOT NULL,
  `before_json` JSON NULL,
  `after_json`  JSON NULL,

```

用 JSON 存前后值，而不是给每张表建历史表（`item_history`、`price_history`…）。代价是查询要解析 JSON、不能强类型；收益是**一张表覆盖所有实体的审计**，加新表不用加历史表。

## 4. `02_logic.sql`：规则与存储程序

### 4.1 `DELIMITER`：一个客户端指令

```sql
DELIMITER $$
CREATE TRIGGER ...
BEGIN
  ...;
  ...;
END$$
DELIMITER ;
```

**`DELIMITER` 不是 SQL 语句，是 mysql 命令行客户端的指令**。客户端默认用 `;` 切分语句，但触发器/存储过程内部有大量 `;`，客户端会在这里误切，导致语法错误。

所以要先告诉客户端“从现在起用 `$$` 当分隔符”，写完再改回 `;`。`$$` 可以换成 `//`、`;;` 等任何不冲突的串。

> 用图形化工具（Navicat/Workbench）或代码执行时，它们有各自的处理方式；`DELIMITER` 只在命令行客户端有效。

### 4.2 触发器：数据库层的“保安”

```sql
CREATE TRIGGER `trg_bom_edge_bi`
BEFORE INSERT ON `bom_edge`
FOR EACH ROW
BEGIN
  DECLARE v_parent_type VARCHAR(16) DEFAULT NULL;
  ...
  IF NEW.`parent_id` = NEW.`child_id` THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'BOM 校验失败：物料不能包含自身';
  END IF;
  SELECT `item_type` INTO v_parent_type FROM `item` WHERE `id` = NEW.`parent_id`;
  ...
END
```

#### `BEFORE` 还是 `AFTER`

| | `BEFORE` | `AFTER` |
|---|---|---|
| 能改 `NEW` 吗 | ✅ 可以（`SET NEW.col = ...`） | ❌ 不能 |
| 能 `SIGNAL` 阻止操作吗 | ✅ 可以 | ❌ 已经写进去了 |
| 典型用途 | 校验、补默认值 | 记审计日志、同步别的表 |

这里的规则是“**不合法就不许写**”，所以必须是 `BEFORE`。

#### `NEW` / `OLD` 伪记录

- `INSERT` 触发器只有 `NEW`；
- `DELETE` 触发器只有 `OLD`；
- `UPDATE` 触发器两者都有。

它们代表**正在处理的那一行**，不是整张表。

#### 为什么跨表校验只能用触发器

`CHECK` 约束不支持子查询，不能引用其它表。而“父件不能是元件”这条规则需要查 `item` 表，所以只能用触发器。

三个规则：

| 规则 | 为什么 |
|---|---|
| 不能包含自身 | `A 含 A` 会让递归立即死循环 |
| 元件不能有子件 | 元件的定义就是“不可再分” |
| 产品不能当子件 | 产品是最终交付物，进 BOM 会造成“产品套产品”的语义混乱 |

#### `SELECT ... INTO` 与 `DECLARE`

```sql
DECLARE v_parent_type VARCHAR(16) DEFAULT NULL;
SELECT `item_type` INTO v_parent_type FROM `item` WHERE `id` = NEW.`parent_id`;
```

两个语法点：

1. **`DECLARE` 必须放在 `BEGIN...END` 块的最前面**，中间任何一条语句之前，否则语法错误。
2. `SELECT ... INTO 变量` 如果查不到行，变量保持原值（`NULL`），并产生 `NOT FOUND` 条件——**不报错**。所以后面用 `= 'component'` 比较，`NULL` 比较结果为 `UNKNOWN`，不会误触发。

#### `SIGNAL SQLSTATE '45000'`

```sql
SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'BOM 校验失败：元件不可再分，不能包含子件';
```

- `45000` 是 SQL 标准里“**未处理的用户自定义异常**”的 SQLSTATE；
- 客户端收到 `ERROR 1644 (45000)`；
- `MESSAGE_TEXT` 上限约 128 字符（够写一句中文说明）。

Qt 侧拿到的是：

```cpp
QSqlError err = query.lastError();
err.nativeErrorCode();  // "1644"
err.databaseText();     // "BOM 校验失败：元件不可再分，不能包含子件"
```

所以**可以直接把 `databaseText()` 弹给用户看**，不需要做错误码映射。

#### 为什么环检测不放在触发器里

递归环检测要遍历子树，成本是 O(子树大小)，而触发器是**按行**执行的——批量插入 1 万条 BOM 边，就变成 1 万次递归。而且触发器抛的错没法携带“环的具体路径”，排查困难。

补充一个硬限制：触发器**修改**自己所在的表会被直接拒绝（`ERROR 1442`）；读取虽然不在此列，但同样要谨慎——行级触发里做重查询，性能会成倍放大。

所以分工是：

- 触发器：**单行、常量时间**的检查（自身、类型）；
- 存储过程：**需要遍历**的检查（环）。

### 4.3 `sp_bom_add_edge`：环检测

```sql
CREATE PROCEDURE `sp_bom_add_edge`(
  IN p_parent_id BIGINT UNSIGNED,
  IN p_child_id  BIGINT UNSIGNED,
  IN p_quantity  DECIMAL(18,4),
  IN p_seq_no    INT,
  IN p_remark    VARCHAR(255)
)
```

#### 参数只有 `IN` / `OUT` / `INOUT`

MySQL 存储过程**没有默认参数值**，可选参数只能传 `NULL` 在过程里判断（如 `p_seq_no` 用 `IFNULL(p_seq_no, 0)`）。

#### 两段式环检测

**第一段：直接环**（O(1) 索引查询）

```sql
SELECT COUNT(*) INTO v_hit
FROM `bom_edge`
WHERE `parent_id` = p_child_id AND `child_id` = p_parent_id;
```

如果 B 已经含 A，现在又要 A 含 B，就是直接环。

**第二段：间接环**（递归 CTE）

```sql
WITH RECURSIVE `sub` AS (
    SELECT p_child_id AS `id`, 1 AS `lvl`
    UNION ALL
    SELECT e.`child_id`, s.`lvl` + 1
    FROM `bom_edge` e
    JOIN `sub` s ON e.`parent_id` = s.`id`
    WHERE s.`lvl` < 20
)
SELECT COUNT(*) INTO v_hit FROM `sub` WHERE `sub`.`id` = p_parent_id;
```

逻辑：把**子件的整棵子树**捞出来，看**父件是否已经在里面**。如果在，说明父件已经间接包含了子件，再加这条边就成环。

#### 递归 CTE 的语法要点

```sql
WITH RECURSIVE cte AS (
  非递归成员（锚）        -- 定义列名、列类型、起始行
  UNION ALL
  递归成员                -- 引用 cte 自己，产生下一层
)
SELECT ... FROM cte;
```

四条规则：

1. **列类型由锚成员决定**。锚里写 `CAST(NULL AS UNSIGNED)`、`CAST(1 AS DECIMAL(18,4))` 就是为了把类型钉死，否则递归成员报“类型不一致”。
2. **递归成员只能引用 CTE 一次**（MySQL 限制）。
3. **递归成员里不能用聚合、窗口函数、`GROUP BY`、`ORDER BY`、`DISTINCT`、`LIMIT`**。
4. **终止条件必须写在递归成员里**（这里 `WHERE s.lvl < 20`）。如果没有终止条件且数据有环，MySQL 会在 `cte_max_recursion_depth`（默认 **1000**）层后报 `ERROR 3636`。

另外两个容易忽略的点：

- **`UNION ALL` 还是 `UNION DISTINCT`**：这里必须 `ALL`。同一个元件可能通过两条不同路径进入同一个产品（菱形 BOM），用 `DISTINCT` 会去重，导致用量少算。
- **递归 CTE 不保证顺序**，要排序必须在外层 `ORDER BY`。

#### 实测：环是能拦住的

```
直接环：ERROR 1644 (45000): BOM 校验失败：A 与 B 已互为父子，会形成循环
间接环：ERROR 1644 (45000): BOM 校验失败：该关系会形成循环包含
```

间接环的测试要造三层结构（A→B→C，再让 C→A），否则测不到递归那一支。

#### `ON DUPLICATE KEY UPDATE`：UPSERT

```sql
INSERT INTO `bom_edge` (parent_id, child_id, quantity, seq_no, remark)
VALUES (p_parent_id, p_child_id, p_quantity, ...)
ON DUPLICATE KEY UPDATE
  `quantity` = VALUES(`quantity`),
  `seq_no`   = VALUES(`seq_no`);
```

语义：**先尝试 INSERT，遇到主键/唯一键冲突就改成 UPDATE**。一次交互完成“有则改、无则加”，省掉一次 `SELECT` 加竞态窗口。

三个要点：

1. `VALUES(col)` 引用“**本来要插入的那个值**”。8.0.20 起官方标记为弃用，推荐用行别名：`INSERT ... AS new ... ON DUPLICATE KEY UPDATE col = new.col`（8.0.19+）。这里保留 `VALUES()` 是为了兼容性——MySQL 仍然支持它。
2. **会消耗自增 id**：即使走了 UPDATE 分支，`AUTO_INCREMENT` 也可能已经 +1，这是自增主键出现空洞的常见原因。
3. 影响行数：`1` = 插入，`2` = 更新，`0` = 值完全相同没改动。实测更新返回 **2**。

#### 为什么过程里不写事务

过程内**不**出现 `START TRANSACTION` / `COMMIT`。原因：

- **`START TRANSACTION` 会隐式提交外层事务**。如果 Qt 那边已经开了事务（“改 BOM + 写审计”），过程里再 `START TRANSACTION` 就把前半截悄悄提交了，回滚不了。
- 事务边界应该由**最清楚业务语义的那一层**（应用服务层）决定，而不是工具层。

所以约定：**存储过程只做“一件事”，事务由调用方管**。

### 4.4 `sp_item_delete`：为什么不直接 DELETE

```sql
SELECT COUNT(*) INTO v_used FROM `bom_edge` WHERE `child_id` = p_item_id;
IF v_used > 0 THEN
  SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '删除失败：该物料仍被其它部件/产品引用';
END IF;
...
UPDATE `item` SET `status` = -1 WHERE `id` = p_item_id;
```

两个决定：

1. **先查引用再删**。虽然 `fk_edge_child` 的 `RESTRICT` 也会拦住，但数据库报的是 `ERROR 1451: Cannot delete or update a parent row`，用户看不懂。这里给的是能直接展示的中文。
2. **软删除**（`status = -1`）而不是 `DELETE`。历史报价单里可能引用它，物理删除会让快照断层；而且软删除保留了 `item_code`，能回答“这个编号以前是什么”。

> `DELETE FROM item` 其实会失败（`RESTRICT`），所以这条路径必须被堵死——这就是为什么要有这个过程：**给出可读的失败原因**。

## 5. `03_sample_data.sql`：示例数据为什么这样造

数据是专门设计成能“一眼验算”的：

```
电气柜 A 型 P-1001  (产品)
├── 线束组件 A-2001 × 1
│   ├── 接线端子 C-3001 × 10   @2.50
│   └── 导线     C-3002 × 5    @1.20
├── 主控模块 A-2002 × 1
│   ├── 控制器   C-3003 × 1    @800.00
│   └── 显示屏   C-3004 × 1    @150.00
└── 保险丝       C-3005 × 2    @无价       ← 故意留空
```

手算：

| 节点 | 计算 | 金额 |
|---|---|---|
| 线束组件 | 10 × 2.50 + 5 × 1.20 | **31.00** |
| 主控模块 | 800.00 + 150.00 | **950.00** |
| 电气柜 | 31.00 + 950.00 + 2 × 0 | **981.00** |

实测输出的正是这三个数（`981.000000000000` / `31.000000000000` / `950.000000000000`，多出的小数位是 `DECIMAL(28,8)` 中间运算的精度，最后在应用层按 2 位四舍五入）。

**为什么故意留一个没价格的元件**：这是需求的核心场景之一——“某些零部件没有价格则提示用户，有价格的数据参与计算”。如果示例数据全都齐备，这个分支永远测不到。

`item_alias` 里的两条客户料号也是同理：不造数据，导入匹配那段代码就永远只走“精确匹配”一条路。

**显式写 `id` 的影响**：`INSERT` 显式指定 `id = 1..8` 后，`AUTO_INCREMENT` 会自动跳到 `max(id)+1`，后续插入不会冲突。

## 6. 实测：约束到底拦住了什么

以下都是在 MySQL 8.0.44 上真实执行的结果：

| 操作 | 结果 |
|---|---|
| 拿元件当父件 `INSERT bom_edge (4, 8, 1)` | `ERROR 1644 (45000): BOM 校验失败：元件不可再分，不能包含子件` |
| 拿产品当子件 `INSERT bom_edge (2, 1, 1)` | `ERROR 1644 (45000): BOM 校验失败：产品不能作为其它物料的子件` |
| 用量为 0 `INSERT bom_edge (2, 8, 0)` | `ERROR 3819 (HY000): Check constraint 'ck_edge_qty' is violated.` |
| 重复编号 `INSERT item ('C-3001', ...)` | `ERROR 1062 (23000): Duplicate entry 'C-3001' for key 'item.uk_item_code'` |
| 删除被引用的物料 `CALL sp_item_delete(4)` | `ERROR 1644 (45000): 删除失败：该物料仍被其它部件/产品引用` |
| 直接环 `CALL sp_bom_add_edge(3, 2, ...)`（已有 2→3） | `ERROR 1644 (45000): BOM 校验失败：A 与 B 已互为父子，会形成循环` |
| 间接环 A→B→C 后 `CALL sp_bom_add_edge(C, A, ...)` | `ERROR 1644 (45000): BOM 校验失败：该关系会形成循环包含` |
| 重复导入同一天价格 | 影响行数 `2`（走了 UPDATE 分支，价格被覆盖） |
| 查 `item_code = 'c-3001'` | 命中 `C-3001`（排序规则大小写不敏感） |
| `MATCH(item_name) AGAINST('端子')` | 命中 `C-3001 接线端子`（ngram 二元切分） |

**这些错误码在 Qt 里怎么处理**：

| 错误码 | 含义 | 界面处理 |
|---|---|---|
| `1062` | 唯一键冲突 | “编号已存在，请换一个” |
| `1451 / 1452` | 外键约束 | “该物料仍被引用/引用的物料不存在” |
| `1644` | 自定义 `SIGNAL` | 直接展示 `databaseText()` |
| `3819` | `CHECK` 违反 | “数量/金额必须大于 0” |
| `1213` | 死锁 | 提示重试（单机几乎不会遇到） |
| `2003` | 连不上服务器 | “MySQL 服务未启动？” |

| 语法 | 出现位置 | 作用 | 注意 |
|---|---|---|---|
| `INSERT ... ON DUPLICATE KEY UPDATE` | 02 upsert | 有则改无则加 | 影响行数 1/2/0 |

### 7.3 查询

| 语法 | 出现位置 | 作用 | 注意 |
|---|---|---|---|
| `LEFT JOIN` | 视图、缺价清单 | 保留左表全部行 | 右表缺失为 NULL |

| `MATCH ... AGAINST` | 04 检索 | 全文检索 | 不能混 `OR` |

| `ORDER BY ... DESC` | 多处 | 排序 | 可反向扫描索引 |
| `GROUP BY + SUM` | 04 汇总 | 聚合 | 受 `ONLY_FULL_GROUP_BY` 约束 |

### 7.4 存储程序

| 语法 | 出现位置 | 作用 | 注意 |
|---|---|---|---|
| `DELIMITER $$` | 02 | 改客户端分隔符 | 仅命令行有效 |
| `CREATE TRIGGER ... BEFORE INSERT` | 02 | 写前校验 | 可改 `NEW`、可 `SIGNAL` |
| `NEW` / `OLD` | 02 | 行记录引用 | INSERT 只有 NEW |
| `DECLARE var TYPE DEFAULT x` | 02 | 局部变量 | 必须在块首 |
| `SELECT ... INTO var` | 02 | 赋值 | 无行时不报错 |
| `SIGNAL SQLSTATE '45000'` | 02 | 抛自定义错误 | 客户端见 1644 |
| `CREATE PROCEDURE ... IN ...` | 02 | 存储过程 | 无默认参数 |
| `CALL proc(...)` | 04 | 调用 | 结果集可逐行读 |

### 7.5 索引原理（不是语法，但决定写法）

| 概念 | 含义 | 影响 |
|---|---|---|
| 聚簇索引 | InnoDB 按主键物理排序存数据 | 主键选择 = 物理布局 |
| 二级索引隐含主键 | `idx(child_id)` 实际是 `(child_id, 主键)` | 反查不用回表 |
| 最左前缀 | 复合索引从左往右匹配 | `WHERE status=?` 用不上 `(type,status)` |
| 覆盖索引 | 查询字段全在索引里 | 不回表，快 |
| 回表 | 二级索引拿到主键再查聚簇索引 | 随机 IO，要避免 |

## 8. 十个容易踩的坑

**1. NULL 与唯一索引**
唯一索引里多个 `NULL` 是允许的（NULL 不等于 NULL）。`UNIQUE(source, alias_code)` 中如果 `source` 可空，唯一性就失效。→ 用 `NOT NULL DEFAULT ''`。

**2. `= NULL` 永远为假**
`WHERE amount = NULL` 返回空集，必须写 `WHERE amount IS NULL`。三值逻辑：`NULL = NULL` 是 `UNKNOWN` 不是 `TRUE`。

**3. ENUM 排序**
`ORDER BY item_type` 按**定义顺序**排，不按字母。要字母序得 `ORDER BY CAST(item_type AS CHAR)` 或 `ORDER BY FIELD(...)`。

**4. 金额用 DOUBLE**
`0.1 + 0.2 ≠ 0.3`。金额一律 `DECIMAL`，C++ 侧用整数放大（`qint64`，×10000），不要用 `double`。

**5. `ON UPDATE CURRENT_TIMESTAMP` 不更新**
值没变就不更新。要强制更新写 `updated_at = NOW()`。

**6. 递归 CTE 没有终止条件**
默认深度 1000，超了报 `3636`。**必须**在递归成员里写深度上限，尤其 BOM 这种可能环的数据。

**7. 递归用 `UNION` 而不是 `UNION ALL`**
菱形 BOM（同一元件经两条路径进入同一产品）会被去重，用量少算。展开 BOM 必须 `ALL`。

**8. 外键自动建索引**
忘了显式建，MySQL 会自动建一个名字不可控的索引，后期想改很麻烦。→ 建表时就写上。

**9. 视图当表用**
视图不存数据、不能建索引，嵌套视图会叠加开销。复杂逻辑要么用物化表（自己维护），要么在应用层算。

**10. `LIKE '%关键字%'` 走不了索引**
前导 `%` 使索引失效。要么用全文索引（中文必须 ngram），要么接受全表扫描（几万行以内可以）。
